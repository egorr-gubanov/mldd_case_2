# Production-внедрение и эксплуатация

## Общая идея production-решения

После успешного пилота система масштабируется на 10 проходных. Архитектура остается гибридной: часть обработки выполняется рядом с КПП, а центральные сервисы отвечают за единые данные, политики доступа, аудит и мониторинг.

Такой подход выбран потому, что проходные физически распределены, а задержка проверки должна быть маленькой. Если каждый запрос полностью зависит от удаленного сервера, краткий сетевой сбой может остановить проход людей. Edge-узел на КПП снижает этот риск.

## Компоненты

| Компонент | Назначение |
| --- | --- |
| Камеры КПП | получение изображения лица |
| Терминал КПП | взаимодействие с сотрудником и оператором |
| Edge Gateway | локальная предобработка, буфер событий, временный fallback |
| Access Control API | бизнес-логика решения о доступе |
| ML Inference Service | извлечение embedding и сравнение |
| Vector Storage | хранение биометрических шаблонов |
| Employee DB | сотрудники, пропуска, статусы допуска |
| Audit Log | неизменяемое хранение событий |
| Admin Panel | управление пользователями, шаблонами и правами |
| Monitoring Stack | метрики, логи, алерты |

## Масштабирование

При 5000 сотрудниках и 10 проходных нагрузка умеренная. Основной пик возникает в начале и конце смен. Для оценки берем запас:

- 10 КПП;
- до 1 запроса в секунду на одну КПП в пике;
- суммарно до 10 RPS;
- хранение нескольких миллионов событий доступа в год;
- поиск по одному шаблону в verification-сценарии и по векторному индексу в identification-сценарии.

Для такого масштаба достаточно горизонтального масштабирования API и ML-сервиса на 2-3 экземпляра. База данных и векторное хранилище должны иметь резервное копирование и мониторинг.

## Безопасность

Так как система работает с биометрическими данными, безопасность является частью архитектуры, а не дополнительной настройкой.

Основные меры:

- хранить не «сырые» фотографии там, где достаточно embedding-шаблонов;
- шифровать данные в покое и при передаче;
- разграничивать доступ по ролям;
- вести аудит действий администраторов;
- ограничивать экспорт биометрических шаблонов;
- хранить журналы отдельно от операционной базы;
- регулярно проверять права доступа;
- иметь процедуру удаления данных уволенных сотрудников.

## Режимы отказа

| Ситуация | Поведение системы |
| --- | --- |
| Плохой кадр | попросить повторить попытку или отправить оператору |
| Низкая уверенность модели | ручная проверка |
| Недоступен ML-сервис | ручной режим на КПП |
| Недоступна сеть | локальный буфер событий и ручной режим |
| Ошибка базы сотрудников | запрет автоматического допуска, ручная проверка |
| Перегрузка очереди | временно увеличить долю операторских решений по регламенту безопасности |

## Эксплуатация

В production нужен регулярный цикл:

1. мониторинг технических метрик;
2. мониторинг ML-метрик;
3. разбор инцидентов;
4. обновление эталонных фотографий;
5. проверка качества по проходным;
6. тестирование новых версий модели;
7. контролируемое выкатывание и возможность отката.

## Почему данные распределены

Данные фактически живут в разных местах:

- кадровые данные — в HR-системе;
- права доступа — в СКУД;
- изображения и события — на КПП и edge-узлах;
- биометрические шаблоны — в защищенном хранилище;
- журналы — в audit storage;
- метрики — в системе мониторинга.

Поэтому архитектура не может быть одной таблицей в одной базе. Нужна интеграционная схема, которая объединяет эти источники, но не смешивает данные без необходимости.
