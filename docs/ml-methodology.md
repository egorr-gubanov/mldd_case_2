# Методология ML и данные

## Тип задачи

Основная задача MVP — **face verification**: система проверяет, совпадает ли лицо человека перед камерой с эталонным шаблоном владельца предъявленного пропуска.

Расширенная задача — **face identification**: система ищет человека по лицу среди всей базы сотрудников. Этот режим полезен, но в MVP мы его не делаем основным, потому что при 5000 сотрудниках выше риск похожих кандидатов и сложнее доказать безопасность решения.

## ML-пайплайн

1. Камера получает кадр.
2. Модуль детекции находит лицо.
3. Модуль качества проверяет резкость, освещение, размер лица и поворот головы.
4. Модель извлекает embedding лица.
5. Сервис сравнивает embedding с эталонным шаблоном сотрудника.
6. Decision engine применяет пороги:
   - высокая уверенность — допуск;
   - низкая уверенность — отказ или ручная проверка;
   - плохое качество кадра — повторная съемка или ручная проверка.
7. Результат сохраняется в журнал.

## Данные

| Данные | Источник | Для чего нужны |
| --- | --- | --- |
| Справочник сотрудников | HR-система | понять, кто работает на предприятии |
| Статусы доступа | система контроля доступа | определить, имеет ли сотрудник право прохода |
| Пропуска | текущая СКУД | связать карту с сотрудником |
| Эталонные фото | HR/служба безопасности | построить биометрические шаблоны |
| События прохода | турникеты и терминалы | анализировать процесс и ошибки |
| Разметка ошибок | оператор и аудит пилота | улучшать пороги и качество |
| Параметры КПП | инфраструктура | учитывать различия камер и освещения |

## Подготовка данных

- удалить дубли сотрудников;
- проверить актуальность пропусков;
- отбраковать плохие фотографии;
- сделать пересъемку для сотрудников без качественного эталона;
- сформировать обучающую и тестовую выборки;
- отдельно собрать набор негативных пар «чужой пропуск — другое лицо»;
- зафиксировать версию датасета и правила доступа к нему.

## Метрики модели

| Метрика | Что показывает | Почему важна |
| --- | --- | --- |
| FAR | доля чужих людей, которых система ошибочно пропустила | основной риск безопасности |
| FRR | доля своих сотрудников, которых система не пропустила автоматически | влияет на очереди и UX |
| TAR при FAR | доля верных допусков при заданном уровне безопасности | помогает выбрать рабочий порог |
| ROC-AUC | качество разделения похожих и разных лиц | удобно для сравнения моделей |
| p95 inference time | скорость ML-части | влияет на очередь у КПП |
| Доля ручных проверок | сколько решений не автоматизировано | показывает бизнес-эффект |

## Выбор порога

Порог сравнения выбирается не только по ML-метрикам, но и по бизнес-рискам. Для промышленного предприятия ошибка ложного допуска обычно опаснее ложного отказа. Поэтому в пилоте выбираем несколько порогов и сравниваем:

- строгий порог: максимум безопасности, больше ручных проверок;
- средний порог: баланс безопасности и скорости;
- мягкий порог: меньше очередей, но выше риск ложного допуска.

Рекомендуемый вариант для production — строгий или средний порог с отправкой спорных случаев оператору.

## Анализ ошибок

Ошибки нужно разбирать не только как «модель ошиблась», а по причинам:

- плохое освещение;
- лицо слишком далеко;
- сотрудник в каске, очках или маске;
- устаревшая эталонная фотография;
- похожие сотрудники;
- неверная привязка пропуска к профилю;
- технический сбой камеры или сети.

Такой анализ поможет понять, что улучшать: модель, данные, оборудование или процесс.

## MLOps

Для промышленной эксплуатации нужны:

- реестр версий моделей;
- версионирование биометрических шаблонов;
- мониторинг распределения embedding-ов;
- контроль drift по проходным;
- регулярная оценка FAR/FRR на размеченных данных;
- процедура отката модели;
- журнал изменения порогов.
